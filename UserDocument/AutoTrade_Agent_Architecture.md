用 Kiro 的 AI Agent 系統（Planner-Generator-Evaluator 模式）去**開發**一個 Auto Trade Program。

## 三、Sub Agent 定義（開發用途）

### Agent 1：Planner（需求分析 + 架構設計）

| 項目 | 內容 |
|------|------|
| **角色** | 分析 Auto Trade 的需求，設計系統架構，拆分開發任務 |
| **輸入** | 用戶需求描述 |
| **輸出** | Spec 文件（requirements.md + design.md + tasks.md） |
| **工具權限** | 只讀（分析 codebase、搜尋參考） |

**職責：**
- 將「我要一個自動交易程式」拆解成具體需求
- 設計系統架構（模組、數據流、API）
- 選擇技術棧（框架、庫、數據庫）
- 拆分成可獨立開發的 Task

### Agent 2：Generator（代碼生成 + 實現）

| 項目 | 內容 |
|------|------|
| **角色** | 根據 Planner 的設計，寫出實際代碼 |
| **輸入** | Spec 文件（tasks.md） |
| **輸出** | 源代碼、測試代碼、配置文件 |
| **工具權限** | 全部（讀寫文件、執行命令） |

**職責：**
- 按 Task 逐步寫代碼
- 寫單元測試
- 寫配置文件
- 確保代碼可運行

### Agent 3：Evaluator（代碼審查 + 測試）

| 項目 | 內容 |
|------|------|
| **角色** | 審查 Generator 寫的代碼，跑測試，提供改善建議 |
| **輸入** | Generator 的代碼 |
| **輸出** | 審查報告（PASS/FAIL + 具體問題） |
| **工具權限** | 只讀 + 執行測試命令 |

**職責：**
- 代碼風格檢查
- 邏輯正確性審查
- 執行測試（unit test / integration test）
- 安全漏洞掃描
- 提供具體修改建議

## 四、開發流程（Planner → Generator → Evaluator 循環）

```
Step 1: 你描述需求
  「我要一個 Python 自動交易程式，支援 Binance，用 RSI 策略」
        ↓
Step 2: Planner 分析
  → 生成 requirements.md（功能需求）
  → 生成 design.md（架構設計）
  → 生成 tasks.md（開發任務清單）
        ↓
Step 3: 你審核 Spec
  → 確認 / 修改需求
        ↓
Step 4: Generator 寫代碼
  → 按 tasks.md 逐步實現
  → 每完成一個 Task 標記完成
        ↓
Step 5: Evaluator 審查
  → 跑測試
  → 檢查代碼質量
  → PASS → 下一個 Task
  → FAIL → 返回 Generator 修正
        ↓
Step 6: 全部 Task 完成
  → 最終整合測試
  → 生成文件
  → 交付
```

## 七、編寫風格規範

### 核心原則
- **Clean Code**：代碼即文件，命名清晰，函數短小
- **Design Pattern**：適當使用設計模式，唔好過度設計
- **解耦**：模組之間低耦合、高內聚，方便獨立測試同替換
- **高效率**：喺唔影響人類理解的前提下，追求執行效率
- **可讀性優先**：效率同可讀性衝突時，優先可讀性

### 函數規則
- 每個函數只做一件事（Single Responsibility）
- 函數長度建議 < 30 行
- 參數數量建議 ≤ 3 個，超過用 dataclass/dict 包裝
- **Loop 嵌套最多 3 層**，超過必須拆分成獨立函數
- 避免深層 if-else 嵌套，用 early return

### 設計模式使用指引

| 場景 | 建議模式 |
|------|---------|
| 多種策略切換 | Strategy Pattern |
| 交易所 API 統一接口 | Adapter Pattern |
| 事件通知（信號、風控） | Observer Pattern |
| 複雜物件建立（訂單） | Builder Pattern |
| 全局配置/連接池 | Singleton Pattern |
| 數據處理流水線 | Pipeline / Chain of Responsibility |

### 解耦規則
- 模組之間透過 Interface/Protocol 通訊，唔直接依賴具體實現
- 使用 Dependency Injection，唔好喺函數內部 hard-code 依賴
- 配置同邏輯分離（config file vs code）
- 數據層同業務層分離（Repository Pattern）

### 代碼結構（每個模組）

```
module/
├── __init__.py          ← 公開 API
├── models.py            ← 數據模型（dataclass）
├── interfaces.py        ← 抽象接口（Protocol/ABC）
├── service.py           ← 業務邏輯
├── repository.py        ← 數據存取
├── exceptions.py        ← 自定義異常
└── tests/
    └── test_service.py  ← 測試
```

### 禁止事項
- ❌ 全局可變狀態（global mutable state）
- ❌ 函數內超過 3 層 loop 嵌套
- ❌ 超過 100 行的函數
- ❌ 超過 500 行的文件
- ❌ Magic number（用常數代替）
- ❌ 註釋解釋「做咩」（代碼本身應該清楚），只註釋「點解」

## 八、自動測試規範

### 測試原則
- **每個模組必須有對應測試**（唔接受冇測試的代碼）
- **測試即文件**：測試用例描述功能行為
- **快速反饋**：單元測試 < 5 秒完成
- **獨立性**：每個測試獨立運行，唔依賴其他測試的執行順序

### 測試分層

| 層次 | 覆蓋範圍 | 數量 | 執行速度 |
|------|---------|:---:|---------|
| Unit Test | 單一函數/類 | 多 | < 1 秒/個 |
| Integration Test | 模組之間互動 | 中 | < 10 秒/個 |
| E2E Test | 完整交易流程 | 少 | < 60 秒/個 |

### 測試框架

| 工具 | 用途 |
|------|------|
| `pytest` | 測試框架 |
| `pytest-asyncio` | 異步測試 |
| `pytest-cov` | 覆蓋率報告 |
| `pytest-mock` / `unittest.mock` | Mock 外部依賴 |
| `hypothesis` | Property-based testing |
| `freezegun` | 時間凍結 |

### 測試命名規範

```python
# 格式：test_[被測函數]_[場景]_[預期結果]
def test_calculate_rsi_with_14_periods_returns_valid_range():
    ...

def test_place_order_when_insufficient_balance_raises_error():
    ...
```

### 覆蓋率要求

| 模組 | 最低覆蓋率 |
|------|:---:|
| 策略引擎 | 90% |
| 風控系統 | 95% |
| 訂單管理 | 90% |
| 數據處理 | 80% |
| UI / 通知 | 60% |

### 必須測試的場景

| 場景 | 測試內容 |
|------|---------|
| 策略信號 | 正確生成買/賣/持有信號 |
| 風控觸發 | 止損/止盈/最大回撤正確觸發 |
| 訂單執行 | 市價單/限價單正確下單 |
| 異常處理 | API 超時/斷線/餘額不足 |
| 數據邊界 | 空數據/缺失數據/極端值 |
| 並發安全 | 多個信號同時觸發唔會重複下單 |
| 回測一致性 | 回測結果同實盤邏輯一致 |

### Mock 規則

| 外部依賴 | Mock 方式 |
|---------|---------|
| 交易所 API | Mock response |
| 數據庫 | In-memory SQLite |
| 時間 | `freezegun` |
| 網絡 | `responses` / `aioresponses` |

### 測試禁止事項
- ❌ 測試依賴外部網絡
- ❌ 測試之間有順序依賴
- ❌ 測試修改全局狀態
- ❌ 跳過失敗的測試（需註明原因）
- ❌ 冇 assertion 的測試

## 十二、同 Kiro 的整合方式

### 方案 A：單一 Workspace + Spec（推薦起步）

```
用 Kiro 的 Spec workflow：
  1. 建立 Spec → requirements + design + tasks
  2. 逐個 Task 執行（Kiro 自動寫代碼）
  3. Hook 自動跑測試
  4. 你審核結果
```

### 方案 B：Multi-Root Workspace（進階）

```
planner/     ← 獨立 Steering（只分析、唔寫 code）
generator/   ← 獨立 Steering（只寫 code）
evaluator/   ← 獨立 Steering（只審查）
auto-trade/  ← 實際程式碼
```

### 建議

先用**方案 A**起步（簡單、快速），等程式複雜到一定程度再考慮方案 B。
